# Deploying with Podman quadlets

This guide runs the songbook as **user-level** systemd services (`systemctl --user`) generated by
Podman [quadlets](https://docs.podman.io/en/latest/markdown/podman-systemd.unit.5.html), behind an
nginx installed on the host. Every component talks over **unix sockets**; none of the containers has
a network (`Network=none`). Nothing needs root except installing nginx and one ACL.

```
                           ~/nginx  (readable by nginx)              $XDG_RUNTIME_DIR/songbook  (private)
 browser ──TLS──> nginx ── gunicorn/gunicorn.sock ──> songbook-web ──┬── postgres/.s.PGSQL.5432 ──> songbook-postgres
           (host)   │                                                ├── redis/redis.sock ────────> songbook-redis
                    │                                songbook-worker ┘          (cache db 0, Huey db 1)
                    ├── /static/ ──> ~/nginx/static   (copied from the image, pre-compressed)
                    └── /media/  ──> ~/nginx/media    (PDFs written by the worker)
```

| Unit | Image | Role |
|---|---|---|
| `songbook-postgres` | `postgres:18` | database, socket in `$XDG_RUNTIME_DIR/songbook/postgres` |
| `songbook-redis` | `redis:8` | Django cache (db 0) and Huey queue (db 1), socket in `$XDG_RUNTIME_DIR/songbook/redis` |
| `songbook-web` | `ghcr.io/pehala/song-book` | `make migrate prerender cache_clear export_static start`: brings the database, cache and nginx's static files up to date, then runs gunicorn on `~/nginx/gunicorn` |
| `songbook-worker` | `ghcr.io/pehala/song-book` | `make worker`: Huey consumer that renders PDFs |

The guide assumes a dedicated, unprivileged user — `songbook` with home `/home/songbook` in the
examples — Podman 5 or newer (for `Notify=healthy`) and an nginx package on the host. All files
referenced live in `deploy/`.

## 1. The image

The `docker` GitHub workflow builds the [`Containerfile`](../Containerfile) on every push to
`main` and publishes it as `ghcr.io/pehala/song-book:latest` (plus a tag per commit sha, for
rollbacks); `ghcr-cleanup` prunes all but the newest ten versions weekly. Pull requests only build
it. If the package is private, run `podman login ghcr.io` as the `songbook` user with a token that
can read packages.

The image installs the `production` dependency group with `uv` and bakes in everything that needs
no database: `make compilemessages collectstatic compress_static`, the last writing a `.br` (brotli
quality 11) and `.gz` (gzip -9) sibling next to every compressible static file. It runs as UID/GID
1001 with `DJANGO_SETTINGS_MODULE=chords.settings.container`.

Its entrypoint is `make` and the container arguments are Makefile targets — the same targets used
outside containers. The units only list them: `Exec=migrate prerender cache_clear export_static start`
for web, `Exec=worker` for the worker. A one-off command works the same way, e.g.
`podman run --rm … ghcr.io/pehala/song-book:latest migrate`.

It is based on Debian slim rather than Alpine on purpose: the PDF index is sorted with
`locale.strxfrm` under `cs_CZ.UTF-8`, and musl has no locale collation, so on Alpine "Č" and "Š"
would sort after "Z" and "Ch" would not follow "H".

To run a local build instead, `make image` (tags `localhost/songbook:latest`) and change `Image=`
in `songbook-web` and `songbook-worker`.

## 2. Prepare the host (as root, once)

```bash
useradd --create-home songbook
loginctl enable-linger songbook              # start the user's services at boot, without a login
setfacl -m u:nginx:x /home/songbook          # nginx may traverse the home, nothing more (Debian: u:www-data)
```

The home directory stays private (`0700`); the ACL only lets nginx *pass through* it to `~/nginx`.
With SELinux enforcing, also see [Permissions and SELinux](#permissions-and-selinux).

Everything else runs as `songbook`. Log in with `machinectl shell songbook@` (or SSH) rather than
`su`, so that `systemctl --user` finds the user's session.

## 3. Prepare the user

Directories for sockets and served files:

```bash
install -D -m 0644 deploy/user-tmpfiles.d/songbook.conf ~/.config/user-tmpfiles.d/songbook.conf
systemd-tmpfiles --user --create
```

The PostgreSQL and Redis sockets go to `$XDG_RUNTIME_DIR/songbook` (`/run/user/<uid>`, private to the
user, recreated at every boot by the same file); what nginx reads goes to `~/nginx`.

Configuration and secrets:

```bash
install -D -m 0600 deploy/songbook.env.example ~/.config/songbook/songbook.env
$EDITOR ~/.config/songbook/songbook.env

python3 -c 'import secrets; print(secrets.token_urlsafe(50), end="")' | podman secret create songbook-secret-key -
python3 -c 'import secrets; print(secrets.token_urlsafe(32), end="")' | podman secret create songbook-db-password -
```

`ALLOWED_HOSTS` must list **every tenant hostname**; adding a tenant later means adding its host
there, to `CSRF_TRUSTED_ORIGINS` and to nginx `server_name`. `TENANT_HOSTNAME` names the default
tenant that the first migration creates. Any other setting can be changed by editing
[`chords/settings/container.py`](../chords/settings/container.py) and rebuilding.

The database password is only read by PostgreSQL's `initdb` on the very first start. Changing the
secret afterwards also needs `ALTER ROLE songbook PASSWORD '…'` inside the database.

## 4. Install the units

```bash
install -D -m 0644 -t ~/.config/containers/systemd deploy/quadlets/*
podman pull docker.io/library/postgres:18 docker.io/library/redis:8 ghcr.io/pehala/song-book:latest
systemctl --user daemon-reload
systemctl --user start songbook-web songbook-worker
```

Starting web pulls in Redis and PostgreSQL, which report ready through their health checks. Web
itself reports ready once gunicorn accepts connections — after the migrations — and only then does
the worker start. All units are `WantedBy=default.target` and the user lingers, so they come back
after a reboot. Logs go to the user's journal: `journalctl --user -u songbook-web -f`.

Create the first superuser:

```bash
podman exec -it songbook-web python manage.py createsuperuser
```

### Why it is laid out this way

- **Sockets, not ports.** No container publishes a port and none has a network, so nothing is
  reachable except through the socket files. The PostgreSQL and Redis sockets sit in the user's
  private runtime directory, so other host users cannot even reach them; PostgreSQL still requires a
  password (`--auth-local=scram-sha-256`) as a second line of defence.
- **One owner for everything.** Rootless Podman maps container users to sub-UIDs, which would leave
  files owned by odd numeric IDs. Every unit instead sets `UserNS=keep-id:uid=<the image's user>`
  (1001 for the app, 999 for PostgreSQL and Redis), which maps that container user to `songbook`.
  Sockets, static files, PDFs and database files on the host are all owned by `songbook`.
- **Web runs the deployment steps before it serves.** There is a single web container, so
  `migrate` runs once per start, before gunicorn opens its socket; the worker `Requires=` web and
  starts after it. `cache_clear` empties the Redis cache database because cached songs JSON built by
  the previous image may no longer match the new frontend's columns; Huey keeps its queue in
  database 1, so scheduled PDFs survive. `migrate` and `prerender` are idempotent, so a restart after
  a crash only costs a few seconds.
- **Read-only containers.** The app containers run with `ReadOnly=true`, no capabilities and
  `NoNewPrivileges`; only `/tmp`, the media directory and the socket directories are writable.

## 5. Upgrade

```bash
podman pull ghcr.io/pehala/song-book:latest
systemctl --user restart songbook-web
```

Web migrates and publishes the new static files before it serves again, and the worker restarts
with it because it `Requires=` web. Web is unavailable for the few seconds the migrations take.

`songbook-web` carries `AutoUpdate=registry`, so `systemctl --user enable --now podman-auto-update.timer`
does the above daily on its own. The worker deliberately has no `AutoUpdate=`: it is restarted
through web, and updating it on its own could start it on new code before web migrated.

Rolling back is the same with a commit sha tag: `podman pull ghcr.io/pehala/song-book:<sha>`, then
`podman tag` it as `latest` before the restart. Migrations are not reversed, so roll back only across
releases that did not change the schema, or restore the database dump as well.

`export_static` keeps previously published static files, so a page loaded before the upgrade can
still fetch its old fingerprinted CSS/JS. To prune them occasionally:

```bash
systemctl --user stop songbook-web
rm -rf ~/nginx/static/*
systemctl --user start songbook-web songbook-worker
```

Backups — the socket requires the password, which the container has in `POSTGRES_PASSWORD`:

```bash
podman exec songbook-postgres sh -c 'PGPASSWORD="$POSTGRES_PASSWORD" pg_dump --username songbook --format=custom songbook' > songbook.dump
```

plus `~/nginx/media` if you want to keep generated PDFs (they can be regenerated). Restore such a
dump the same way as in [step 4 of the migration](#6-migrating-an-existing-deployment).

## 6. Migrating an existing deployment

For moving a running non-container deployment (gunicorn from a checkout with its own
`chords/settings/production.py`, PostgreSQL on the host) to the quadlets. The old deployment is
left untouched, so switching back is just re-enabling it. The site is down from step 3 to step 7,
usually a few minutes.

The examples assume the old checkout in `/home/songbook/song-book`, run by the same `songbook`
user, and its database `chords`; adjust the names. Commands are run as `songbook` unless marked
*root*.

**1. Prepare the new deployment** with [steps 2–3](#2-prepare-the-host-as-root-once), except for
the secret key: reuse the old one, so sessions and password-reset links stay valid:

```bash
cd ~/song-book
uv run python -c 'from chords.settings import production; print(production.SECRET_KEY, end="")' \
  | podman secret create songbook-secret-key -
```

In `~/.config/songbook/songbook.env`, `ALLOWED_HOSTS` and `CSRF_TRUSTED_ORIGINS` must cover every
existing tenant (step 5 lists them); `TENANT_HOSTNAME` does not matter, the database already has
its tenants.

**2. Install the units and start only PostgreSQL** — starting web now would migrate an empty
database and create a default tenant that then collides with the restored one:

```bash
install -D -m 0644 -t ~/.config/containers/systemd deploy/quadlets/*
podman pull docker.io/library/postgres:18 docker.io/library/redis:8 ghcr.io/pehala/song-book:latest
systemctl --user daemon-reload
systemctl --user start songbook-postgres
```

**3. Stop the old deployment** so nothing writes to the old database any more (*root*; use the
names of your old gunicorn and Huey units):

```bash
systemctl stop <old gunicorn unit> <old huey unit>
```

**4. Dump the old database and restore it.** Dump in custom format, without owners and grants: the
new database belongs to the `songbook` role whatever the old role was called (*root*):

```bash
runuser -u postgres -- pg_dump --format=custom --no-owner --no-privileges chords > /home/songbook/songbook.dump
chown songbook: /home/songbook/songbook.dump
```

Restore it into the new, still empty database in one transaction, so a failure leaves nothing
half-restored:

```bash
podman exec -i songbook-postgres sh -c \
  'PGPASSWORD="$POSTGRES_PASSWORD" pg_restore --username songbook --dbname songbook --no-owner --no-privileges --single-transaction --exit-on-error' \
  < ~/songbook.dump
```

A dump from an older PostgreSQL major version restores into 18 as is. If the restore fails half way
(it rolls back), recreate the empty database and repeat:

```bash
systemctl --user stop songbook-postgres
podman volume rm songbook-postgres
systemctl --user start songbook-postgres
```

**5. Check the tenants** against `ALLOWED_HOSTS` and nginx `server_name`:

```bash
podman exec songbook-postgres sh -c \
  'PGPASSWORD="$POSTGRES_PASSWORD" psql --username songbook --dbname songbook --tuples-only --no-align --command "SELECT string_agg(hostname, chr(44)) FROM tenants_tenant"'
```

**6. Copy the generated PDFs.** The old `MEDIA_ROOT` is `chords/media` relative to the old unit's
working directory:

```bash
cp -a ~/song-book/chords/media/. ~/nginx/media/
```

**7. Start the app and switch nginx.** Web applies any migrations newer than the old checkout,
prerenders and publishes the static files before it serves:

```bash
systemctl --user start songbook-web songbook-worker
journalctl --user -u songbook-web -f        # wait for "Listening at: unix:/run/gunicorn/gunicorn.sock"
```

Then, as *root*, replace the old site's nginx config with
[`deploy/nginx/songbook.conf`](../deploy/nginx/songbook.conf) (section 7) and reload:

```bash
nginx -t && systemctl reload nginx
```

**8. Clean up** once the site works, as *root*: `systemctl disable <old gunicorn unit> <old huey unit>`.
Keep the old database and checkout until you are sure; switching back is reverting the nginx config
and starting the old units again. PDF generations that were queued in the old Redis are not carried
over — regenerate them from the PDF pages if needed.

## 7. nginx

Install [`deploy/nginx/songbook.conf`](../deploy/nginx/songbook.conf) (nginx 1.25.1+ for `http2 on`) into `/etc/nginx/conf.d/`,
set `server_name` to all tenant hostnames, point the certificate paths at yours and replace
`/home/songbook` if the user's home differs. Highlights:

- `proxy_pass` goes to `unix:/home/songbook/nginx/gunicorn/gunicorn.sock`.
- `Host` is passed through untouched: the tenant is chosen from it, and an unknown host is a 404.
- `X-Forwarded-Proto` tells Django the request was HTTPS (`SECURE_PROXY_SSL_HEADER`); the container
  settings mark session and CSRF cookies `Secure`, so the site has to be served over HTTPS.
- A catch-all `default_server` drops requests for hostnames that are not tenants (`return 444`, and
  `ssl_reject_handshake` for unknown TLS names). Remove it if the host already has a default server.
- `/static/` and `/media/` are served by nginx straight from `/home/songbook/nginx`. Django does not
  serve either with `DEBUG = False`.

### Compression

There are two kinds of content, and they are compressed differently.

**Static files: pre-compressed, never on the fly.** They are compressed once at image build time at
the highest levels — far smaller than nginx would produce per request, at zero runtime CPU.
`brotli_static on` / `gzip_static on` make nginx look for `file.css.br` / `file.css.gz` and send it
when the client's `Accept-Encoding` allows, falling back to the plain file. Do not add
`brotli on`/`gzip on` with static types *in the static location* expecting a gain — the `_static`
lookup already wins. Images, `woff`/`woff2` fonts and PDFs are already compressed and are skipped.

**Dynamic responses: compressed by nginx, not by Django.** The page shell is small; the response that
matters is the songs JSON (`/all/data`, `/categories/<slug>/data`), which carries every song's
rendered HTML and is very repetitive — it typically shrinks 5–10×. Use moderate levels
(`brotli_comp_level 4–6`, `gzip_comp_level 4–6`): higher levels cost a lot of CPU for a few percent.
Keep Django's `GZipMiddleware` off; compressing in nginx keeps gunicorn workers free.
`gzip_proxied any` is needed so that clients behind another proxy (which send `Via`) still get
compressed responses, and `gzip_vary on` adds `Vary: Accept-Encoding` so caches keep the variants apart.

**ETags survive compression.** The JSON views send a strong ETag and `Cache-Control: no-cache`, so a
returning browser revalidates and gets a `304` with no body. When nginx compresses a response it
downgrades the ETag to a weak one (`W/"…"`); Django compares `If-None-Match` weakly, so the 304
still works. Check it after deploying:

```bash
etag=$(curl -sI -H 'Accept-Encoding: br' https://songs.example.org/all/data | grep -i '^etag' | cut -d' ' -f2- | tr -d '\r')
curl -s -o /dev/null -w '%{http_code}\n' -H 'Accept-Encoding: br' -H "If-None-Match: $etag" https://songs.example.org/all/data
# expect 304
```

and that statics come pre-compressed (look for `content-encoding: br` and a long `cache-control`):

```bash
curl -sI -H 'Accept-Encoding: br, gzip' https://songs.example.org/static/<path printed in the page source>
```

**BREACH.** Compressing HTML that contains a secret together with attacker-reflected input can leak
the secret. Django masks the CSRF token differently in every response, which is the standard
mitigation; nothing else secret is rendered into pages.

**No brotli module?** It is not part of stock nginx. Debian/Ubuntu ship it as
`libnginx-mod-http-brotli-filter` and `libnginx-mod-http-brotli-static`; elsewhere it may need to be
built ([google/ngx_brotli](https://github.com/google/ngx_brotli)). Without it, delete the `brotli*`
lines: gzip alone still serves the pre-built `.gz` files and compresses the JSON.

### Caching headers

- Fingerprinted statics (`styles.3f2a9c1b7d0e.css`) are `immutable` with a one-year `max-age`; their
  name changes whenever their content does. The `map` in the config tells them apart from the
  un-fingerprinted copies `collectstatic` also writes, which only get an hour.
- `/media/` is `no-cache`: a category's PDF is regenerated under the same file name.
- Dynamic pages and JSON carry the headers Django sets; do not override them in nginx.

### Slow clients

The site is meant for camps with a bad connection, so a download can take a long time. A gunicorn
thread would be blocked for all of it, which is why `proxy_buffering` stays **on**: nginx takes the
whole response from gunicorn in a few milliseconds and feeds the slow client itself. The buffer
sizes in the config keep the songs JSON in memory instead of spilling to a temporary file.

### gunicorn

[`deploy/gunicorn.conf.py`](../deploy/gunicorn.conf.py) runs 2 `gthread` workers with 4 threads each
(the app is mostly cache reads, so threads are cheap concurrency), recycles workers every ~1000
requests, and logs access to the journal. Over a unix socket gunicorn sees no client address, so the
access log records `X-Forwarded-For` from nginx instead, plus the duration in milliseconds. Override
anything with `GUNICORN_CMD_ARGS` in `~/.config/songbook/songbook.env`, e.g. `--workers 3`.

### Permissions and SELinux

nginx needs three things from the `songbook` user's files, all of which the setup above gives it:

- search (`x`) permission on `/home/songbook` — the ACL from step 2; nothing in the home is listable;
- `~/nginx` and everything below it world-readable (`0755` directories, `0644` files);
- the gunicorn socket writable: gunicorn creates it `0777` (`umask = 0`). Only users that can traverse
  the home — `songbook` and nginx — can reach it.

With SELinux enforcing, the `:z` volume option labels the shared directories `container_file_t` so
the containers can use them; the host's nginx (`httpd_t`) is not allowed to read that label, to
connect to a container's socket, or to enter a home directory by default. As root, allow the home
directory and install the small policy module in
[`deploy/selinux/songbook_nginx.te`](../deploy/selinux/songbook_nginx.te):

```bash
setsebool -P httpd_enable_homedirs 1
cd deploy/selinux
checkmodule -M -m -o songbook_nginx.mod songbook_nginx.te
semodule_package -o songbook_nginx.pp -m songbook_nginx.mod
semodule -i songbook_nginx.pp
```

If nginx logs `Permission denied` anyway, `ausearch -m avc -ts recent | audit2allow` shows what is
still missing.

## Troubleshooting

| Symptom | Look at |
|---|---|
| nginx `502`, `connect() to unix:/home/songbook/nginx/gunicorn/gunicorn.sock failed` | `systemctl --user status songbook-web`; `(13: Permission denied)` means the home ACL or SELinux |
| every page `404` | the request's host is not a `Tenant.hostname` (edit tenants in `/admin/`) |
| `400 Bad Request` | host missing from `ALLOWED_HOSTS` |
| `403 CSRF verification failed` on login | origin missing from `CSRF_TRUSTED_ORIGINS`, or `X-Forwarded-Proto` not set |
| web never becomes ready, worker never starts | `journalctl --user -u songbook-web` — a failing `make` target (e.g. a migration) stops it before gunicorn |
| PDFs stay queued | `journalctl --user -u songbook-worker` |
| units do not start after a reboot | `loginctl show-user songbook -p Linger` must say `yes` |
| `statfs …/songbook/postgres: no such file or directory` | `$XDG_RUNTIME_DIR/songbook` missing: is `~/.config/user-tmpfiles.d/songbook.conf` installed? |
| `Failed to connect to bus` from `systemctl --user` | logged in with `su`; use `machinectl shell songbook@` or SSH |
