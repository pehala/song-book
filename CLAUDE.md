# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**chords** — a multi-tenant Django songbook (`https://github.com/pehala/song-book`). Songs are
written in Markdown with a custom chord syntax, served **once** as JSON to the browser, and
filtered/searched entirely client-side so the site stays usable on a bad connection (camps,
wilderness). It also generates printable PDF songbooks asynchronously.

Stack: Python 3.14, Django 6, `uv`. Production runs PostgreSQL plus Redis (both the cache and
the Huey queue) under gunicorn behind nginx, which serves fingerprinted static files
pre-compressed with brotli (`brotli_static`) and long-lived cache headers; dev and tests use
SQLite and an in-memory cache.

## Commands

Everything runs through `uv`. **Never invoke bare `python`/`pytest`.**

```bash
uv sync --group dev                 # install deps (dev group)
make dev                            # dev server on SQLite (chords.settings.development): no make init, no Redis; PORT, DB_FILE
make init                           # cp production.py.tpl -> production.py, then migrate
make run                            # dev server (SETTINGS=chords.settings.production, needs Redis)
make worker                         # Huey worker for PDF generation
make test                           # uv run --group dev pytest tests/
make coverage                       # the same, with a branch coverage report
make e2e                            # Playwright tests of the reader (needs `uv run playwright install --with-deps chromium`)
make commit-acceptance              # what CI gates on: ruff --fix + ruff format + check-fuzzy + check-messages
make migrations                     # makemigrations
make messages                       # makemessages -l cs --no-location
make deploy                         # migrate + prerender + compilemessages + collectstatic
make image                          # podman build of the Containerfile
make help                           # all targets
```

Single test / subset:

```bash
uv run --group dev pytest tests/backend/test_etag.py::test_response_has_etag -v
uv run --group dev pytest tests/ -k cache
uv run --group dev pytest tests/ -m "not slow and not e2e"    # skip the real WeasyPrint renders
```

Management commands: `uv run python manage.py <cmd>` — notably `prerender`,
`clear_prerender`, `import -c <category_id> <file.json>`, `generate_pdf`, `run_huey`.

CI (`.github/workflows/songbook.yml`) runs `make init`, `make commit-acceptance`, `make test`, and in a second job
installs Chromium and runs `make e2e`.

## Settings

| Module | Role |
|---|---|
| `chords/settings/base.py` | all shared defaults, custom settings and cache-key names |
| `chords/settings/development.py` | `make dev`: SQLite `db.sqlite3` of the working tree (or the `DB_FILE` env var; the port is `PORT`), `DEBUG = True` (unhashed static files), in-memory cache, `HUEY` immediate, prerendering on; nothing to generate |
| `chords/settings/production.py` | **not committed** — generated by `make init` from `production.py.tpl`; Redis cache, real `SECRET_KEY`/`ALLOWED_HOSTS`, `DEBUG = False`, prerendering on |
| `chords/settings/container.py` | used by the container image; reads env vars, reaches PostgreSQL/Redis over unix sockets |
| `chords/settings/test.py` | LocMemCache, plain `StaticFilesStorage`, test `SECRET_KEY`, `ALLOWED_HOSTS` |

`manage.py` and the Makefile default to `chords.settings.production`, so **a fresh clone cannot
run anything until `make init` has created that file**, except `make dev`, which passes `--settings` itself. pytest is pinned to
`chords.settings.test` in `pyproject.toml`.

Base settings use `chords.storage.ManifestStorage`, a `ManifestStaticFilesStorage` that also
rewrites `import … from "./x.js"` inside hashed modules; tests must not use it (hence the
override) because no manifest is collected. Hashed URLs are only emitted with `DEBUG = False`,
and with `DEBUG` off nginx has to serve `/media/` (see the README). `SECURE_CSP` (Django 6 CSP middleware) is enforced — adding a CDN script
or inline style means editing that policy.

## Multi-tenancy

One deployment serves several songbooks, told apart by `Host` header.

- `tenants/middleware.py` resolves `Tenant` by `hostname` and sets `request.tenant` plus
  `request.user.is_localadmin` on **every** request. Unknown host → 404, except under `DEBUG`
  where it falls back to `Tenant.objects.first()`.
- `tenants/migrations/0001_initial.py` creates a default tenant with
  `hostname=settings.TENANT_HOSTNAME` (`"localhost"`). Tests must `get_or_create` it, not
  `create` it, and the test `Client` needs `HTTP_HOST="localhost"` for the middleware to resolve.
- `Song` has **no** FK to `Tenant`. The path is always `song → categories → tenant`, which is why
  tenant-scoped song querysets filter on `categories__tenant` and `.distinct()`.
- Every cache key is namespaced: `tenant_cache_key(tenant, key)` → `f"{tenant.id}-{key}"`
  (`tenants/utils.py`).

## Apps

| App | Contains |
|---|---|
| `backend` | `Song`, the songs payload, `/api/me` and song CRUD views, generic CRUD base views, auth helpers, mixins, management commands |
| `category` | `Category` (a **subclass of `pdf.PDFTemplate`**), category admin views |
| `pdf` | `PDFTemplate`/`ManualPDFTemplate`/`PDFFile`/`PDFSong`, WeasyPrint generation, Huey tasks |
| `tenants` | `Tenant`, `Link`, the hostname middleware, tenant admin/move views |
| `analytics` | `DayStatistic` per tenant/key/day, the `analytics()` counter, bumped once per `/api/songs` request |
| `frontend` | no models — the reader (`ShellView`, `ServiceWorkerView`, `ManifestView`, `shell.html`, `static/app/*`, the header context processor) and the Bootstrap base templates of the admin pages (`base/index.html`, `base/frame.html`, `base/verbs/*`), global CSS, icon font |

Cross-app glue worth knowing before editing:

- **CRUD views** inherit `UniversalCreateView`/`UniversalUpdateView`/`UniversalDeleteView` from
  `backend/generic.py` (success messages, `?next=` redirect, `base/verbs/*.html` templates).
  Access control is `LocalAdminRequired` / `SuperAdminRequired` from `backend/mixins.py`, backed
  by `backend/auth.py`.
- **Navigation** is drawn client-side by the shared header from the tenant's bootstrap (`tenants/bootstrap.py`),
  whose categories, PDFs and links come from the cached menus in `tenants/menus.py`.
- **URLs**: `backend.urls` is mounted at `^` (so `/`, `/all`, `/api/songs`, `/api/me`, `/add`,
  `/edit/<pk>`), `frontend.urls` serves `/service_worker.js` and `/manifest.webmanifest`, categories live at
  `/categories/<slug>`, plus `/pdf/`, `/analytics/`, `/tenants/`,
  `/admin/`. `/`, `/all` and `/categories/<slug>` all route to `frontend.views.ShellView`.

## Song rendering pipeline

Markdown → HTML happens through the mistune instances of `chords/markdown.py`, each with three
local plugins in `chords/plugins/`: a chord plugin — `inline` (`{Ami}` → `<span class="chord">`), `ruby`
(`{Ami}word` → `<ruby>word<rt class="chord">`) or `raised` (PDF only) — `paragraph` and `spaces`.
`INLINE_RENDERER` uses the first, `RUBY_RENDERER` the second, and the `SONG_RENDERER` setting (a dotted path,
`RUBY_RENDERER` by default) picks the one used for songs and for django-markdownx's preview; a changed
renderer needs `manage.py prerender`.

PDFs use `PDF_RENDERER` (`Song.pdf_markdown`) instead, whatever `SONG_RENDERER` says; `docs/PDF_LAYOUT.md`
describes how their chords, header link and running footer are laid out.

`Song.rendered_markdown` chooses between rendering on the fly and the stored `prerendered`
column, controlled by two settings:

- `USE_PRERENDERED_MARKDOWN` — serve `Song.prerendered` instead of re-rendering.
- `USE_DYNAMIC_PRERENDER` — when a song has no prerendered HTML, render and save it on first
  request; with both the first off and the second off, a missing value raises.

`make deploy` runs `manage.py prerender` to fill the column for every song.

## The reader

The reader (song list, search, category switching, song view) is a Preact + htm single page app
with no build step. Everything else (CRUD, PDF, analytics, login, `/admin/`) keeps its Django
templates and Bootstrap from the CDN.

- Some of those server pages have their content drawn by Preact too: the template keeps the title, renders an
  empty `#page` and the page's data as `page-data` JSON and loads a page entry (`progress.js` for
  `/pdf/files/wait/<pk>`, `analytics.js` for `/analytics/`), which calls `mountPage` from `page.js`. The data
  names the JSON endpoints the page calls, and the strings are `_("…")` msgids of the reader's catalogue,
  translated into the language of `<html lang>`.
- The header (`header.js`: `SiteHeader`, which draws the bar, the notices and the QR dialog from the state of
  `useSiteHeader`) is one Preact component used twice: by the
  reader and, through `site.js`, by every Bootstrap page. `base/index.html` has an empty `#site-header`, the
  `boot` and `me` JSON (from `frontend.context_processors.header`, evaluated only when printed) and loads
  `site.js`; the Python-side menus are gone, so a menu entry is added in `header.js` only. Header markup and
  `header.css` use `sb-` prefixed classes so they cannot clash with Bootstrap, and the theme is the
  `data-bs-theme` attribute on `<html>` (set early by an inline script, then by `options.js`), which both
  Bootstrap and the reader's CSS follow. Pages the server renders (`server: true`) take their language from
  `<html lang>`, change it by POSTing `setlang` and reloading, and leave out the options that need songs.
- `ShellView` serves **one** page, `frontend/templates/shell.html`, for `/`, `/all` and
  `/categories/<slug>`: the stylesheets as `<link>`s (`STYLESHEETS`), an SVG sprite, `modulepreload` links, a
  `preload` of `/api/songs` and the tenant's bootstrap JSON in `<script id="boot">`
  (`tenants/bootstrap.py: bootstrap_payload`, built from the entries the navigation menus keep in the
  cache, so menu invalidation covers it). It reads no user, session, message, CSRF or language, so
  there is no `Vary: Cookie`; it gets an ETag and `Cache-Control: no-cache`. An unknown category slug
  gets the same body with status 404. Keep it that way: the service worker serves one cached copy to
  every route and every user. `RecognizeTenantMiddleware` resolves `is_localadmin` lazily for the
  same reason.
- Modules are in `frontend/static/app/` (`app.js` entry, `site.js` entry for server pages, `header.js`, `options.js`, `songs.js`, `store.js`,
  `i18n.js`, `page.js` and the page entries, `vendor/preact-htm.module.js`, `vendor/qr.mjs`, `header.css`, `app.css`)
  and listed once in `frontend.views` (`MODULES`, `SITE_ENTRY`, `PAGE_ENTRIES`/`PAGE_MODULES`, `STYLESHEETS`), which
  feeds the preload links and the service worker's precache. A new file must be added there. Keep modules
  free of import cycles (hashing needs a DAG) and `import()` out of modules with nested template
  literals: `ManifestStorage` cannot see past them.
- The CSS is mobile first (`min-width` queries), every control is at least 44 px, form fields use 16 px text, text
  meets WCAG AA contrast in both themes and animations stop under `prefers-reduced-motion`;
  `tests/e2e/test_layout.py` checks all of it, so keep colours in the `--*` variables of `header.css`.
- `/api/me` (`MeView`) is the only place that knows the user: `auth`, `username`, `localadmin`,
  `superuser`, plus the pending `django.contrib.messages`, which it drains; the CRUD views still redirect
  to the shell and the toast arrives through here. It is `private, no-store` and sets the CSRF cookie.
- The client keeps UI options in `localStorage` (`theme`, `lang`, `columns`, `hide_chords`,
  `prevent_sleep`; `theme` keeps the key the Bootstrap pages use), fetches songs through `store.js`
  (Cache API entry `songs`: draw the stored list, revalidate, replace it when the ETag changed; deleted
  on logout). Statistics are counted by the server: each `/api/songs` request, which the reader makes once per
  open, adds a hit under the key `all`.
- `ServiceWorkerView` renders `frontend/templates/service_worker.js` per tenant: the cache name hashes the precached
  urls and carries the tenant id, the shell is cache-first with background ETag revalidation
  (`ignoreVary`), `/static/*`, the manifest and the logo are cache-first, everything else (including
  `/api/*`) goes to the network. A new worker waits; the page shows a toast and sends `skipWaiting`.
  Reader routes in `service_worker.js` (`READER`) must stay in step with the URLconf.

## Songs payload + caching

`GET /api/songs` (`SongsApiView`, `chords:songs_api`) returns every song of the tenant as one JSON
list with the slugs of its categories in `cats`; the browser filters it per route and numbers the list
itself (non-archived songs first, archived ones appended).

- It looks the JSON **string** up in the cache first and only on a miss builds it through
  `backend/songs.py` (`cached_songs_payload` → `build_songs_payload` → `songs_to_json`, with a
  tenant-filtered `Prefetch` of the categories). A hit or a 304 costs one cache read.
  `transform_song()` fixes the field order of each row.
- Cache keys per tenant: `{id}-SONGS` and `{id}-SONGS_archived` (`songs_payload_key`). The
  `_archived` variant is chosen by `is_superuser`, the only users who see archived songs, and is served
  `private`; tenant admins share the public entry.
- Invalidation is signal-driven. Receivers at the bottom of `backend/models.py` clear both variants for
  the affected tenants on `Song` save/delete, on `Song.categories` membership changes (captured on
  `pre_remove`/`pre_clear`, so the old categories are covered, and cleared again on `post_remove`/`post_clear`) and on `Category` save/delete
  (including the previous tenant), plus the `CATEGORY_CACHE_KEY` menu entry. The helpers are in
  `backend/cache.py`: `invalidate_tenant_songs_cache(tenant)` and the per-song wrapper
  `invalidate_songs_cache(song)`. Invalidation inside a transaction (the Django admin saves in `atomic()`) waits for the commit through
  `transaction.on_commit`; the tests' autouse `run_on_commit_at_once` runs those callbacks at once, and tests of the
  deferral use `real_on_commit`. Views do **not** invalidate by hand; the one exception is
  `CategoryMoveView`, whose `bulk_update` sends no signals.
- A `pre_save` receiver refreshes `prerendered` on every full `save()` while
  `USE_PRERENDERED_MARKDOWN` is on (a save with `update_fields` skips it), so admin edits and
  scripts cannot leave it stale; `bulk_create` sends no signals, so `manage.py import` prerenders
  before it.
- `GET /api/songs?since=<epoch seconds>` with the stored ETag in `If-None-Match` answers a 304 when the list is
  current and otherwise `{etag, now, ids, changed}` (`build_songs_delta`, `no-store`): `ids` is every visible
  song in list order, which numbers them, and `changed` the full rows with `Song.updated_at >= since`.
  `updated_at` is bumped by `auto_now`, which only a `save()` triggers, and by `touch_songs()` wherever rows
  change without one: category membership changes, category save/delete, `CategoryMoveView` and
  `manage.py prerender`; any other `update()`/`bulk_update()` that alters a displayed field must call it too.
  `store.js` (`mergeDelta`) merges the delta into the stored list, asking from 60 s before the
  stored copy's `Date`, and falls back to the whole list when the delta does not fit. The shell therefore does
  not `preload` `/api/songs`.
  Both response kinds carry the uncompressed byte length in `X-Songs-Size`; `store.js` reads the body in chunks and
  reports `{loaded, total}`, which `app.js` draws as a progress bar while no list is stored and as a thin line along
  the top while a stored list is being brought up to date (hidden for the first 300 ms).
- `ETagJsonMixin` hashes the cached JSON (blake2b) into an ETag and returns 304 via
  `get_conditional_response`, with `Cache-Control: no-cache`.

## PDF generation

`PDFTemplate` is a django-polymorphic model and the configuration for a PDF; `Category`,
`ManualPDFTemplate` and `AllSongsTemplate` (the virtual all songs category, one per tenant, created on first
open of the category list) are its concrete subclasses, each supplying `get_songs()`. Generating
creates a `PDFFile` row (status `QUEUED`/`SCHEDULED`/`IN_PROGRESS`/`DONE`/`FAILED`) and schedules
the Huey task `generate_pdf_job`, which renders `pdf/index.html` through WeasyPrint under the
template's locale and saves the file.

Category PDFs regenerate automatically on song/category change via
`request_pdf_regeneration()` (and, for the tenant's `AllSongsTemplate`, `request_all_songs_pdf_regeneration()`), delayed by `CATEGORY_PDF_DELAY` (30 min) so an editing spree
batches into one file; it is skipped while the template already has an unfinished file.
`docs/FILES.md` describes the template/file workflow, `docs/PDF_LAYOUT.md` the page layout.

Locally, set `HUEY = {"immediate": True}` in `chords/settings/production.py` to run generation
inline instead of running `make worker`.

## Container deployment

`Containerfile` builds one image for web and worker. Its entrypoint is `make`, so container
arguments are Makefile targets: the build bakes in `compilemessages collectstatic compress_static`,
web runs `migrate prerender cache_clear export_static start`, the worker runs `worker`. Keep those
targets working without uv (the image sets `RUN` empty). `deploy/` holds the guide (`deploy/DEPLOY.md`), the quadlet
templates, the `songbook@.target`, gunicorn config, user tmpfiles.d entries, nginx config and SELinux modules. The
quadlets are user-level (`systemctl --user`) **templates**, one instance per songbook, started through
`songbook@<instance>.target` (`enable` is refused for generated units); `UserNS=keep-id` makes files on the host belong
to the service user, which is also the PostgreSQL role (peer authentication); containers have `Network=none` and
talk over unix sockets in `$XDG_RUNTIME_DIR/songbook/<instance>` and `~/nginx/<instance>`. The PostgreSQL of the host is
the default (its `/run/postgresql` is mounted as it is); `deploy/postgres-container/` swaps in a PostgreSQL container
with a unit, drop-ins and two `sed` lines. Keep the units free of quoted arguments in `HealthCmd=` (older quadlet generators
drop a closing quote).

## Conventions

- All imports at the top of the file; no inline imports. Signal receivers therefore live in the
  models modules (`backend/models.py`, `tenants/models.py`), not in an `AppConfig.ready()`.
  Where a module needs both `functools.cache` and Django's cache, alias the latter:
  `from django.core.cache import cache as django_cache`.
- Comments and docstrings describe what the code does now — never the previous behaviour, the
  change being made or why it differs from before. That belongs in the commit message.
- Do not add new `_`-prefixed methods unless something genuinely must stay internal; give the
  method a public name, or make it a module-level function. The same goes for reading protected
  members of other objects (`_meta`, `_base_manager`) when a public API exists.
- The reader's strings are English gettext msgids written `_("…")` in `frontend/static/app/*.js` (the name
  `_` is what `xgettext` extracts, so keep it and use literals only). `make messages` extracts them into
  `chords/locale/cs/LC_MESSAGES/djangojs.po`; `frontend/catalogues.py` reads the compiled catalogue and
  `bootstrap_payload` carries it as `i18n`, so both the shell and the server pages translate without a request.
  `make check-messages` (part of `commit-acceptance`) regenerates `djangojs.po` and fails when it differs from
  the committed file or has an untranslated string.
- Every user-visible string goes through `gettext_lazy`/`gettext_noop`. Czech is the default
  language; `make check-messages` also regenerates `chords/locale/cs/LC_MESSAGES/django.po` and fails when it
  differs from the committed file, and `make check-fuzzy` fails the build if either catalogue contains fuzzy
  entries, so run `make messages`, resolve them and commit both files. The catalogues carry no source locations
  (`--no-location`), so they change only when a string or its translation does.
- ruff, line length 120, target `py314` (`.python-version` is 3.14). The `D` (pydocstyle) rules run with the Google
  convention, so every module, package, class, function and method has a docstring: a summary line ending in a period,
  in the descriptive third person (`"""Returns ..."""`; D401 is off), with a blank line before any further text.
  `__init__`, magic methods and nested `Meta` classes are exempt (the class docstring covers them), and migrations
  and the `__init__.py` files of `tests/` are not checked. A method that overrides a framework hook still says what
  it does here.
- Dev dependencies: `uv add --group dev <pkg>`.
- One logical change per commit.
- No fixup commits in the final history: a fix to code a commit of the same branch introduced is
  folded into that commit (`git commit --fixup` + `git rebase --autosquash`), tests included, so
  the branch never contains a commit that repairs an earlier one.
- Conventional Commits for commits and PR titles: `type(scope): summary` — types `feat`, `fix`,
  `perf`, `refactor`, `test`, `docs`, `ci`, `chore`; scopes `backend`, `frontend`, `category`,
  `tenants`, `pdf`, `ci`, `settings`.

## Tests

`tests/` is a pytest-django suite split per app (`tests/backend/`, `tests/category/`,
`tests/pdf/`, `tests/tenants/`, `tests/chords/`, `tests/analytics/`, `tests/frontend/`), plus two suite-wide
modules: `tests/test_url_permissions.py`, a parametrized matrix asserting login redirect, 403
and allowed access for every URL in the project, and `tests/test_menus.py`. Each directory is a
package — the `__init__.py` files are what keep same-named modules such as
`backend/test_models.py` and `category/test_models.py` from colliding.

`tests/conftest.py` provides the shared fixtures: `tenant`/`other_tenant`, `category`, `song`,
`archived_song`, the `make_category`/`make_song` factories, `manual_template`, `pdf_file`,
`superuser`/`staff_user`/`plain_user` and the matching `Client` fixtures. Three autouse fixtures
clear the cache, flush the task queue and point `MEDIA_ROOT` at a `tmp_path`, so generated PDFs
and uploads never reach the source tree. A session-scoped autouse fixture, `compiled_messages`, compiles the `.po` files with `msgfmt` into a
temporary directory and points `LOCALE_PATHS` there, so the tests run in the default language (Czech) with real translations whatever
`.mo` files lie in the source tree; assert the Czech strings. The e2e browser is pinned to `en-US`
(`browser_context_args`), so the reader is English there until a test switches the language. `tests/pdf/conftest.py` adds the PDF-only fixtures and
overrides `manual_template` and `media_root` for that directory; fixtures used by a single
module live in that module. The initial migration already seeds a category for the default
tenant, so tests look categories up by slug rather than assume the fixture is the only one.
`tests/backend/test_signals.py` covers the signal-driven invalidation and prerender-on-save;
`tests/chords/test_storage.py` runs a real `collectstatic` into a `tmp_path` to check that hashed
modules import hashed modules.

`tests/e2e/` drives the reader in Chromium through Playwright (pytest-playwright against pytest-django's
`live_server`) and is excluded from the default run by `addopts = "-m 'not e2e'"`; `make e2e` runs it.
Its `library` fixture builds a two-category songbook, `sign_in(user)` puts a session cookie into the
browser, and `DJANGO_ALLOW_ASYNC_UNSAFE` is set so the test thread can use the ORM next to Playwright's
event loop. The live server shares one in-memory SQLite database, so wait for the page to go idle before
writing from the test. There is no JS unit test runner: behaviour of the client is covered here.

It runs on SQLite against `chords.settings.test`; production uses PostgreSQL and Redis, so
anything cache- or tenant-related is exercised through LocMemCache here. Those test settings run
Huey with `immediate=True`, so a task scheduled without a delay renders inline — tests that do
not want a real PDF use the `mock_weasyprint` fixture, and the few that do are marked `slow`
(`pytest -m "not slow"` skips them). Passwords are hashed with MD5 there: the default PBKDF2
hasher costs ~200 ms per user and the tests sign in with `force_login()`.

Coverage is configured in `pyproject.toml` (branch coverage, migrations/`apps.py`/`wsgi.py` and
the uncommitted `production.py` omitted) and currently sits at 100%; `make coverage` reports it.
